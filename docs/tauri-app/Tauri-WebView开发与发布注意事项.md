# Tauri WebView 开发与发布注意事项

## 2026-11-19 11:23

适用范围：本项目 `apps/tauri-app`，Tauri 2、Vue 3、Dockview 工作台。本文结合当前源码整理开发、部署和测试事项，未修改应用配置，也未进行跨平台实机验证。

关联文档：[业务组件 JSON 配置方案](./方案设计.md)、[标签休眠与内存管理方案](./工作台标签休眠与内存管理方案.md)。

### 1. 先明确运行环境

Tauri 使用平台提供的 WebView。开发服务器在 Chrome 中正常，并不等于打包后的所有目标系统均正常。

| 平台 | 主要 WebView | 需要关注 |
| --- | --- | --- |
| Windows | Microsoft Edge WebView2，基于 Chromium | 运行时安装和更新、企业策略、显卡及远程桌面环境 |
| macOS | WKWebView，基于 WebKit | 系统版本相关的 WebKit 能力、字体、输入法和窗口行为 |
| Linux | WebKitGTK | 支持发行版、系统依赖和 WebKitGTK 版本差异 |

项目需要定义实际支持的操作系统、最低版本和 CPU 架构，并在这些环境验证。不要把当前开发机的能力当成用户机器的最低能力，也不要把某个平台的 WebView 进程模型直接套到另一平台。

### 2. 本项目当前配置与代码观察

以下路径相对于 `apps/tauri-app/`。

| 检查位置 | 已观察到的情况 | 后续注意事项 |
| --- | --- | --- |
| `src-tauri/tauri.conf.json` | 使用 Tauri 2 配置，`bundle.targets` 为 `all` | 仍需分别准备目标平台构建和验证环境 |
| 同上 | 未显式配置 Windows `webviewInstallMode` | 核实当前 Tauri 版本默认行为，明确在线/离线部署策略；缺省不代表安装包完全不处理运行时 |
| 同上 | 已设置 CSP | 新增接口、Worker、资源域名时测试发布包的实际限制 |
| `src-tauri/capabilities/` | 主窗口和子窗口使用不同能力配置 | 新功能需要验证其所属窗口的权限，而非只测主窗口 |
| `src/store/modules/tp/index.ts` | 前端完整解析和序列化工程 JSON | 大工程可能产生主线程停顿和瞬时内存峰值 |
| 同上 | recent project 和 last opened file 信息写入 localStorage | 这些记录不足以恢复未保存的业务内容 |
| `src-tauri/src/commands/fs.rs` | 读写调用 `std::fs`；保存使用 `fs::write` | 当前保存实现不等同于临时文件替换式原子保存 |
| 工作台编辑区 | 所有已打开面板持续挂载业务子树 | 大量标签需要实施独立的组件休眠策略 |
| 业务编辑器与面包屑 | 多处使用 `navigator.clipboard.writeText` | 测试平台差异、调用条件和失败反馈 |

### 3. Windows WebView2 部署

用户机器必须具备兼容的 WebView2 Runtime。不能仅凭其安装了 Edge，便认为发布应用的运行环境已完整验证。

发布前明确选择：

- 在线部署：安装器检测并按需引导安装运行时，验证代理、企业策略和网络失败场景。
- 离线部署：按目标架构准备对应离线方案，验证无网络、无预装运行时的干净系统。
- 如采用 Fixed Version Runtime：评估包体积、架构适配和后续安全更新责任。

`webviewInstallMode` 的具体可选值、安装器行为和权限条件，以实施时锁定的 Tauri 版本文档为准。不要直接复制旧版本配置。

建议保留两类测试环境：开发常用机器，以及没有开发依赖的干净 Windows 虚拟机或实机。

### 4. 跨引擎的界面兼容性

本项目重点验证 Dockview 分屏、标签拖拽、嵌套滚动、业务表格和界面缩放。

#### 4.1 尺寸、缩放与拖拽

- 覆盖 Windows 系统缩放 100%、125%、150%，以及应用自身缩放的组合。
- 覆盖 Retina/普通屏幕与跨屏拖动，验证尺寸和坐标重新计算。
- 当前 WorkbenchEditor 对 Dockview 网格执行缩放抵消，业务内容另行缩放；调整这部分 CSS 后必须回归拖拽落点、分隔条、菜单位置和命中区域。
- 改变侧栏宽度、窗口大小、字体大小和主题后，表格与图表应及时重新布局。
- 布局尚未可测量的隐藏组件，不应把零尺寸当成最终尺寸缓存。

#### 4.2 字体、输入与浮层

- 覆盖中文输入法组合输入、候选框、连续输入和快捷键冲突。
- 覆盖下拉菜单、Tooltip、弹窗和 Teleport 在缩放及分屏中的定位。
- 覆盖 flex/grid 下的最小宽高、长文本省略和滚动条差异。
- 检查鼠标、触控板、右键菜单及原生文件拖拽与应用内部拖拽是否冲突。
- 发布包离线打开时，字体、图标和必要资源应能正常使用。

优先通过目标引擎实测确认兼容性；需要新浏览器 API 时先做能力检测，并提供明确的缺失处理。

### 5. 100 个业务标签与内存

现有业务标签位于同一前端 WebView 环境中。标签没有天然的独立进程边界，应用需要自行卸载长期不用的业务子树。

- 按标签休眠方案保留标签和共享业务数据，卸载业务组件、DOM 及组件资源。
- 分屏中所有实际可见面板均受保护，不能只保留全局激活标签。
- 使用条件渲染卸载业务子树；隐藏 DOM 或 KeepAlive 缓存实例不等同于完成回收。
- 组件卸载时清理图表、监听器、定时器、观察器、组件订阅和失效请求。
- 检查全局 Map、事件总线和生命周期注册回调是否继续引用已卸载组件。
- 动态 import 已加载的代码通常留在模块缓存中，不能承诺随业务组件一起卸载。

内存测量同时观察业务实例数、DOM 数、订阅数量、堆内存趋势和应用相关进程内存。单看操作系统某一个进程数字，可能无法准确反映共享服务、图形资源和运行时缓存。

生产策略优先采用闲置时间、后台实例数量和业务能力声明。浏览器专有的 `performance.memory` 等接口不作为跨平台必需能力，也不依赖生产环境强制垃圾回收。

### 6. 大 JSON、主线程与 IPC

当前读取链路大致为：Rust 读取完整文件 → IPC 返回字符串 → 前端 `JSON.parse` → Store 保存对象。

保存链路大致为：前端 `JSON.stringify` → IPC 传输完整字符串 → Rust 写文件。

注意事项：

1. JSON 解析、序列化、排序和大量 DOM 创建都可能阻塞前端主线程；函数返回 Promise 不意味着其中的同步工作自动移出主线程。
2. 完整字符串、解析后的对象以及 IPC 序列化结果可能在一段时间内同时存在；峰值内存可能明显高于文件大小。
3. `shallowRef` 能减少深层响应式代理开销，但不会消除 JSON 解析、字符串分配或表格渲染成本。
4. 大表格优先使用虚拟化和按需展示，避免一次生成全部行节点。
5. 重计算可评估 Worker 或 Rust 后台任务；Worker 消息的结构化克隆仍可能复制数据，不应假定换成 Worker 就没有内存代价。
6. 把 JSON 放到 Rust 解析后又完整传回前端，仍可能保留大量数据跨边界传输成本。应结合业务评估只传当前数据切片、批量 patch 或查询结果。
7. 当前 Rust 命令虽然声明为 async，内部仍调用同步 `std::fs`。大文件读写需评估阻塞任务调度；CPU 密集工作和阻塞 I/O 应按实际负载放到合适的执行环境。

使用真实大小的工程样本测量打开、编辑、保存、休眠和恢复时的耗时与峰值，再决定是否引入分块存储和更复杂的数据服务。

### 7. 业务数据与异常恢复

需要区分三个层次：

| 层次 | 典型事件 | 数据保留要求 |
| --- | --- | --- |
| 组件卸载 | 标签休眠、右侧切换 | Store 数据保留，必要 UI 状态有快照 |
| WebView 重载或异常退出 | 页面刷新、运行环境故障 | JS 内存 Store 可能丢失，需要落盘草稿或恢复日志 |
| 应用/系统中断 | 崩溃、断电、强制退出 | 依赖已经可靠写入磁盘的内容及恢复机制 |

现有“最近工程”和“上次打开文件”记录只帮助定位文件，不能代替未保存编辑内容的备份。

建议后续增加独立的数据保护设计：按工程维护草稿或增量恢复日志，提供恢复提示，并明确保存成功的判定时机。

当前底层保存使用 `fs::write`，与 Store 注释中“原子保存”的表述存在差异。后续应评估在同一文件系统写临时文件、完成必要刷新后安全替换的流程，并验证 Windows 文件占用、权限、磁盘满及中断场景。替换的具体语义和断电持久性需要按平台实现，不能仅凭 rename 就宣称所有场景安全。

保存期间如果允许继续编辑，应记录保存快照的数据版本，完成后只清理已保存版本对应的脏状态，避免把后续修改误标为已保存。多个窗口同时编辑同一工程时，也需要明确写入所有权或冲突策略。

### 8. 浏览器 API、CSP 与 Tauri 能力

常见需要单独验证的能力包括剪贴板、文件访问、下载、全屏、窗口控制和后台请求。

- 剪贴板调用应处理用户手势、权限和平台失败，成功提示放在调用成功之后。
- 在普通浏览器开发环境与 Tauri 环境之间明确区分能力；浏览器中的“保存成功”不能被当作原生文件已写入的证明。
- 开发服务器的 origin 与发布包的协议/origin 不同。接口的 CORS、Cookie、认证、证书、代理和存储行为需要在发布包重新验证。
- 当前 CSP 已限制脚本、连接和资源来源。新增 Worker、blob 资源或接口域名时按实际需要修改，并测试发布构建；不要用全量放开 CSP 掩盖配置问题。
- Tauri capability、WebView 浏览器权限和 Rust 自定义命令的数据校验是不同层次，某一层通过不代表其他层自动放行或已经完成校验。
- 主窗口与子窗口权限不同，新增能力需在对应窗口验证。Rust 文件命令还需结合实际调用入口处理路径与访问范围。

JSON 业务配置继续采用已注册组件名及受限路径绑定；可执行表达式、任意模块路径和原生命令调用不放入配置。

### 9. 多窗口、后台计时与资源所有权

- 新建独立 WebView 窗口会带来额外运行资源，应按实际窗口数量测量。
- 不同窗口拥有各自的前端 JS 状态，Pinia 不会自动跨窗口共享；同步需要显式事件或后端数据服务。
- 单例连接、全局快捷键和持续任务明确由主窗口或后端服务拥有，避免每个子窗口重复初始化。
- 窗口关闭、标签休眠和组件卸载是不同生命周期，分别释放其拥有的资源。
- 窗口后台、最小化或系统休眠时，计时器和动画回调可能被延迟或暂停；不要依赖 setInterval 精确执行关键业务任务。
- 标签休眠时间使用时间差判断，窗口恢复可见时重新评估；实际任务调度放在适合的服务层。

### 10. 白屏、卡死和显卡环境排查

遇到白屏或冻结时先区分故障层次：

1. 前端：资源路径、启动异常、组件错误、CSP 拦截、主线程长任务。
2. 原生与权限：Rust 命令失败、capability、文件权限、插件初始化。
3. 运行环境：WebView2 Runtime、目标系统依赖、企业策略和代理。
4. 图形环境：显卡驱动、虚拟机、远程桌面、图表/WebGL 资源。

记录应用版本、系统版本、架构、运行时版本（平台支持时）、窗口布局、缩放比例和复现步骤。先查看前端及 Rust 日志，再用最小页面、关闭特定重组件等方式缩小范围。

不要把所有白屏都归因于 GPU，也不要预先全局关闭硬件加速；具体处理应基于已复现环境及平台支持的配置。

Vue ComponentErrorBoundary 可以隔离部分组件异常，但不能保障整个 WebView 进程崩溃后的数据，也无法自动消除主线程阻塞。

### 11. 发布验证矩阵

按实际承诺支持的平台选择环境，至少覆盖最低支持环境和一个当前常用环境。

| 维度 | 建议覆盖 | 重点观察 |
| --- | --- | --- |
| Windows 运行时 | 已安装、未安装、无法联网 | 安装和首次启动 |
| Windows 图形环境 | 普通实机；客户使用时增加远程桌面/虚拟机 | 白屏、渲染与拖拽 |
| macOS | 最低支持系统、常用系统；按承诺覆盖架构 | WebKit、输入法与浮层 |
| Linux | 实际支持的发行版和依赖版本 | 安装、启动及 WebKitGTK 行为 |
| 缩放 | 系统 100%/125%/150%，应用缩放，跨屏 | Dockview 尺寸与坐标 |
| 数据规模 | 小样本、典型工程、真实大工程 | 主线程延迟、峰值内存与保存 |
| 标签数 | 1、10、100；休眠/恢复重复操作 | 实例回收、状态和资源泄漏 |
| 业务交互 | 多分屏、右侧切换、表格、图表、中文输入 | 数据归属、状态恢复与布局 |
| 文件异常 | 无权限、磁盘满、文件占用、保存失败 | 原文件与未保存状态 |
| 会话异常 | 页面重载、异常退出后重新启动 | 草稿恢复和错误反馈 |

最低检查应使用正式构建产物，而非只运行 Vite 开发服务器。`bundle.targets: all` 表示打包目标选择，不意味着一次构建自动完成所有操作系统的可用安装包。

### 12. 建议优先级

P0：明确客户目标平台及 WebView2 离线部署方式；确认生产包可启动、可打开工程、可正确保存；验证大工程是否阻塞；明确异常退出时未保存数据的保护范围。

P1：验证 Dockview 缩放和分屏兼容；实施标签休眠与组件资源清理；完善大文件保存、UI 草稿恢复和多窗口状态归属。

P2：根据测量决定是否将解析和计算移至 Worker/Rust、引入数据切片服务，以及增加更细的诊断和用户设置。
